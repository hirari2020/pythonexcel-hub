自律型コーディングエージェント徹底整理

── Windows 11・WSL有無で分類する（2026年5月版）

「Claude Code のように、自律的にローカルのファイル操作・コマンド実行・プログラム実行ができるツール」は、2026年現在、数十種類が乱立している。本稿ではそれらを Windows 11 で WSL 無しに使えるかどうか を主軸に分類・整理する。

1. この分野の全体像

「Claude Code 的なツール」とは、チャット補完型ではなく エージェント型 ── 「ゴールを伝えると、計画を立て、ファイルを編集し、シェルコマンドを実行し、テストを走らせ、失敗を読んで自己修正するループを回す」ツールを指す。

2026年に入って起きた構造変化は次の5点：

  1. ベンダー4強の確立 ── Claude Code（Anthropic）/ Codex（OpenAI）/ Antigravity（Google）/ Kiro（Amazon）。
  2. IDE型から CLI型・自律型へ重心シフト ── GitHub Copilot 的な補完型から、ターミナル常駐エージェント／クラウド自律エージェントへ。
  3. マルチエージェント・オーケストレーション化 ── 単一エージェントとの「ペアプロ」から、git worktree で分離した複数エージェントの並列管理へ。
  4. GitHub Copilot の新規個人サブスク停止（2026年4月） ── 推論コンピュート需給逼迫が背景。
  5. Agent Skills（SKILL.md）のオープン標準化 ── Anthropic が Claude Code 向けに作った SKILL.md 形式が、ツール横断のオープン標準「Agent Skills」として広がった。スキルとは手順・スクリプト・参照資料をまとめた再利用可能な能力パッケージで、一度書けば対応する複数ツールで使い回せる。本稿では各ツールに スキル対応 の有無を注記する（✅＝SKILL.md/Agent Skills 対応を確認）。

エージェントの実行能力は3レベルで捉えられる：

  • ファイル操作: 複数ファイルの読み書き・差分編集・リファクタリング
  • コマンド実行: シェルコマンド、ビルド、git 操作、テスト実行
  • 自律ループ: 上記を「テストが通るまで」自動で反復、人間は承認・監督役

そして本稿の主題に関わる 重要な前提変化 がある。2025年前半まで、CLI 系エージェント（特に Claude Code）は Windows では WSL 必須というのが常識だった。しかし2025年後半〜2026年にかけて主要ツールが続々と ネイティブ Windows 対応 を果たし、状況は大きく変わった。古い記事や SEO 記事には「WSL 必須」と書かれたままのものが多いので注意が必要だ。各ツールの Windows・WSL 観点での分類は第8章にまとめた。

2. ベンダー4強

2026年のこの分野は、4つのテック大手が出す純正エージェントが中心軸になっている。Anthropic の Claude Code、OpenAI の Codex、Google の Antigravity、Amazon の Kiro ── いずれも自社の最新モデルと深く統合され、設計思想と得意領域がはっきり分かれる。まずこの4強を押さえると、全体像がつかみやすい。

大づかみに言えば、Claude Code と Codex は「ターミナルから使う CLI 型」、Antigravity と Kiro は「エージェント管理を軸に設計されたスタンドアロン IDE 型」である。そして 4製品とも Windows 11 でネイティブに動作し、WSL は不要 だ（各ツールの Windows 対応の詳細は第8章の分類表も参照）。

Claude Code（Anthropic）── CLI 型

  • 種別: CLI / IDE拡張 / Web / Desktop / Mobile の5環境
  • Windows: ✅ WSL 不要（2025年7月 v1.0.51 〜）。irm https://claude.ai/install.ps1 | iex または winget install Anthropic.ClaudeCode。Git for Windows 推奨、無ければ PowerShell フォールバック
  • ライセンス: プロプライエタリ
  • 自律実行: ファイル操作・コマンド実行・git・テスト・自律ループすべて対応。「文脈収集→実行→検証」の agentic ループ。重大な変更には人間承認を要求する安全設計
  • 特徴: CLAUDE.md + Hooks でプロジェクト固有ルールを徹底。1Mトークンのコンテキスト。subagents で専門特化した並列エージェントを起動可能
  • スキル対応: ✅ Agent Skills（SKILL.md）の発祥元。標準そのものの実装元で、context フォーク等の独自拡張も持つ
  • Computer Use: 2026年3月24日に macOS 版、4月3日に Windows 版がリサーチプレビュー公開（Pro/Max 向け）
  • デスクトップアプリ: 2026年4月14日に刷新、複数セッションの並列管理に対応（Pro/Max/Team/Enterprise 向け）。Windows 版あり
  • 価格: Claude Pro（$20/月）または Max（$100・$200/月）に含まれる。API 従量課金も可
  • バージョン目安: v2.1.84（2026年4月時点）
  • 備考: 2026年2月時点で GitHub 公開コミットの約4%を占めるとの推計（SemiAnalysis）。GitHub スター約83K

Codex / Codex CLI（OpenAI）── CLI 型

  • 種別: CLI（ローカル）+ クラウド（ChatGPT 統合）+ IDE 拡張 + Codex アプリ（GUI）
  • Windows: ✅ WSL 不要。CLI は PowerShell + ネイティブ Windows サンドボックス（config.toml で elevated/unelevated）。winget 利用。Codex アプリ（GUI）も Windows ネイティブ。※注意: VS Code 拡張のエージェントモードは一時期 WSL 必須だったが、ネイティブ Windows サンドボックスが実験的→広く利用可になった
  • ライセンス: OSS（CLI 部分）
  • 自律実行: 2026年2月にリニューアル。クラウドサンドボックスでコード実行、GitHub への直接プッシュ可能。Full Auto モードで自律実行。ネイティブ Windows ではエージェントモードが Windows サンドボックスで作業フォルダ外への書き込み・ネットワークアクセスをブロック
  • 特徴: GitHub 統合（PR/Issue に @codex タグでレビュー・自動修正）。Automations で Issue triage・CI/CD 監視を自律実行。音声入力対応
  • スキル対応: ✅ Agent Skills（SKILL.md）対応。2025年12月に対応開始し、~/.agents/skills/ に配置。openai.yaml メタデータの独自拡張あり
  • モデル: GPT-5 系 / Codex 系（GPT-5.1-Codex-Max は Windows コード生成・ツール利用が改善）
  • 価格: ChatGPT Plus または Pro プランで利用。CLI 自体は無料、API キーでも可
  • バージョン目安: 0.104.0（2026年2月時点）。WSL1 は Codex 0.114 までサポート、0.115 以降は bubblewrap 移行で WSL1 非対応

Google Antigravity ── IDE 型

  • 開発元: Google
  • 種別: ゼロから「エージェント管理」を軸に再設計された AI-IDE（スタンドアロン）。2025年11月ローンチ
  • Windows: ✅ WSL 不要。Windows ネイティブアプリ
  • 自律実行: Agent Manager（Manager View）で複数エージェントを並列管理。エージェント制御ブラウザで E2E テストまで自動化。Artifacts（計画・差分・スクリーンショット・テスト結果）と自己検証ステップ（Verifications）が特徴
  • モデル: Gemini 3 Pro が中心。Antigravity 内では Claude 系モデル（Sonnet/Opus）等も使え、エージェントごとに別モデルを割り当て可能。ただし自前の API キー持ち込み（BYOK）には非対応
  • スキル対応: ✅ Agent Skills（SKILL.md）対応
  • ★無料枠（$0 プラン）はあるが大幅縮小された（重要）:
    • 無料 Individual プラン（$0/月、クレカ不要）は現在も存在。どのティアでも Gemini 3 Pro・無制限タブ補完・Agent Manager・ブラウザ統合などの全機能にアクセス可
    • ローンチ時（2025年11月〜2026年2月）: 無料枠 1日250リクエスト、5時間ごとにクォータ補充
    • 2026年3月の変更後: 無料枠 1日20リクエスト（約92%減）、補充は週次（約24倍遅い）。Pro も約100リクエスト/日へ縮小、補充週次化
  • クレジット制（2026年3月導入）: クォータ超過分はクレジットで購入。$25 で 2,500クレジット（1クレジット $0.01）、$199 で 20,000クレジット。1クレジットがトークン/操作量でいくらに相当するかは非公開
  • 有料プラン: AI Pro $20/月、AI Ultra $249.99/月。Pro→Ultra の価格差は12.5倍と極端
  • ★注意点: 段階的な制限削減とクレジット制導入により、日常利用者が数日間（最長168時間＝7日間）ロックアウトされる事例が多発。2026年3月12〜13日に The Register・DevClass 等が価格改定を報道し、大きな開発者の反発を招いた
  • 総評: 無料で試す価値は高いが「free to start」であって「free forever」ではない

Amazon Kiro ── IDE 型

  • 開発元: Amazon
  • 種別: AI-IDE（スタンドアロン）
  • Windows: ✅ WSL 不要。Windows ネイティブアプリ
  • 特徴: スペック駆動開発。仕様を起点にコードを生成・検証するアプローチで、品質管理に強み
  • スキル対応: ✕ SKILL.md（Agent Skills）には非対応。仕様駆動の独自 hooks 機構を持つ（4強の中ではここだけ標準スキル非対応）
  • 位置づけ: 4強の中では最も「品質ゲート」を重視する設計

3. その他のベンダー製 CLI エージェント

4強以外で、各 LLM プロバイダーが自社モデル向けに出している公式 CLI。モデルとの統合が深いのが共通点。

Gemini CLI（Google）

  • 種別: CLI（OSS）
  • Windows: ✅ WSL 不要。Node.js ベースでネイティブ動作
  • ライセンス: OSS
  • 自律実行: ReAct ループ、組み込みツール、MCP 対応。ファイル操作・コマンド実行可
  • 特徴: Google アカウントがあれば無料で利用可能。無料枠が主要ツールの中で最も寛容。Gemini Code Assist とクォータ共有
  • 弱点: コーディング用途には若干不向きという評価もある
  • スキル対応: ✅ Agent Skills（SKILL.md）対応
  • 価格: 無料枠あり
  • バージョン目安: v0.29.0（2026年2月時点）
  • 補足: CLIProxyAPI を使うと Gemini CLI の無料枠を OpenAI 互換 API としてラップでき、Aider や Cline からも無料で叩ける

Qwen Code（Alibaba Cloud）

  • 種別: CLI（OSS、Apache-2.0）。Google Gemini CLI をベースにしている
  • Windows: ✅ WSL 不要。Windows 用 .bat インストーラあり。Node.js 22+ 必須
  • 自律実行: ワークフローツール＋リポジトリ操作。LSP 対応、バッチランナー
  • スキル対応: ✅ Agent Skills（SKILL.md）対応（GA 済み）
  • モデル: Qwen3-Coder / Qwen3.6-Plus 系
  • 性能: マルチファイル対応、SWE-Bench スコアは有料ツール上位と競合する実力との評価
  • GitHub スター: 約24.3K
  • ★無料枠は廃止された（重要）:
    • 無料枠はもともと Qwen OAuth 経由で1日1,000リクエストだった
    • 2026年4月13日: 1日1,000 → 100リクエストに即時削減
    • 2026年4月15日: Qwen OAuth 無料エントリーポイントを完全廃止。キャッシュ済みトークンは一時的に動く場合があるが、新規リクエストは拒否される
  • 現在の認証・利用方法（3択）:
    1. Qwen OAuth ── qwen.ai アカウントでブラウザログイン。無料枠は廃止済み
    2. Alibaba Cloud Coding Plan ── Alibaba Cloud の API キーによる有料サブスク。モデル選択肢が豊富（Qwen / GLM / Kimi / Minimax 等）で高クォータ。Coding Plan Pro は月額 $50
    3. API Key ── 自前の API キーを持ち込み。OpenAI / Anthropic / Gemini など互換エンドポイントに対応
  • 無料の代替: OpenRouter、Fireworks AI、Alibaba Cloud ModelStudio が公式に案内されている。また Qwen のモデル自体はオープンソースのままなので、ローカル（Ollama 等）で動かす分には引き続き無料（ただし高性能モデルは相応のハードウェアが必要）
  • 背景: Alibaba の Qwen チームが主要人材離脱後にプロプライエタリ開発へ舵を切りつつあるとの報道（FT）。中国系 AI 企業 MiniMax もほぼ同時期にライセンスを変更しており、「中国系 OSS モデルの無料戦略の転換」という文脈で語られている

Kimi CLI（Moonshot AI）

  • 種別: CLI
  • Windows: 要確認（公式の Windows ネイティブ対応状況は未検証）
  • 特徴: オープンソースモデル Kimi K2.6 系。商用最高峰モデルに追従する OSS モデルとして、機密性の高いコードを社内環境で動かしたい用途で現実的な選択肢になりつつある
  • 備考: SWE-Bench Pro で上位との報道

4. OSS の CLI / ターミナル常駐エージェント

特定ベンダーに縛られず、モデルを自由に選べる（BYOM = Bring Your Own Model）のが共通の強み。Ollama 経由でローカルモデルを使えばモデルコストゼロも可能。

OpenCode（sst/opencode）

  • 開発元: SST 社
  • Windows: ✅ WSL 不要。Windows ネイティブバイナリ提供（Go 製）
  • ライセンス: MIT
  • 自律実行: 完全自律エージェント。計画・シェルコマンド実行・出力読み取り・失敗修正のループ
  • 特徴: OSS の AI コーディングツールで最多スター（約153K）。Claude Code の直接的な OSS 代替と位置づけられる。75以上のモデルプロバイダー対応（Models.dev 経由）。LSP 統合。マルチセッション対応（同一プロジェクトで複数の並列エージェント）。リンク経由のセッション共有。プライバシー優先設計でコード・コンテキストを保存しない。GitHub Copilot や ChatGPT Plus アカウントでの認証にも対応
  • アーキテクチャ: クライアント/サーバー型。PC で実行しながらモバイルから操作可能
  • スキル対応: ✅ Agent Skills（SKILL.md）対応。.opencode/skills/ のほか .claude/skills/・.agents/skills/ も読み込み、必要時にオンデマンドでロードする
  • 価格: 完全無料・OSS。デスクトップ版ベータあり（Windows 対応）
  • バージョン目安: v1.2.10（2026年2月時点）
  • 位置づけ: 「汎用の標準的選択肢」。リポジトリ編集が主タスクならまずこれ

Aider

  • 種別: OSS の CLI、老舗（2023年7月以前から存在）
  • Windows: ✅ WSL 不要。pip install aider-chat（Python）
  • ライセンス: OSS
  • 自律実行: 差分/パッチでのファイル編集。git ネイティブでマルチファイルワークフローに強い。コードベースのインデックス作成、ファイル編集時の自動 lint・test 実行
  • 特徴: モデル非依存・BYO API キー。Claude / GPT / Gemini / DeepSeek / Ollama・LM Studio 経由のローカルモデルを指定可能。git 履歴を尊重し、変更ごとにコミット
  • 得意: 「3ファイルにまたがる関数リネーム」のような、構造化された計画が不要で素早く回したいタスク。クリーンな git 履歴を保ちたい用途
  • スキル対応: ✅ Agent Skills（SKILL.md）対応
  • ベンチマーク: 精度・実行時間・トークン使用量のバランスが最も良いとの評価（ある比較で複合スコア52.7%、257秒、126kトークン）
  • GitHub スター: 約27〜44K（集計ソースにより幅）
  • バージョン目安: v0.86.0（2026年2月時点）

Goose

  • 開発元: Block 社（旧 Square）→ その後 Linux Foundation（Agentic AI Foundation）に寄贈
  • Windows: ✅ WSL 不要。Rust 製で Desktop アプリは macOS/Linux/Windows ネイティブ。CLI も公式が「ネイティブ Windows 実行を推奨」と明記（Git Bash 推奨、または PowerShell）。歴史的には WSL 推奨だったが2026年時点でネイティブ成熟。※ Windows では keyring が不安定なため、API キーは環境変数で設定するのが定石
  • ライセンス: Apache-2.0
  • 種別: デスクトップアプリ + CLI + API
  • 自律実行: 実行・編集・テストが可能なローカル動作の自律エージェント。MCP ネイティブ統合
  • 特徴: コードだけでなく開発環境全体を横断（Web 閲覧、DB クエリ、テスト実行、ドキュメント読解）。Recipes で再利用可能なマルチステップ・ワークフローを定義。Docker 不要。15以上のプロバイダー対応（Anthropic/OpenAI/Google/Ollama/OpenRouter/Azure/Bedrock 等）。既存の Claude/ChatGPT/Gemini サブスクを ACP 経由で使うことも可能
  • スキル対応: ✅ Agent Skills（SKILL.md）対応（独自の Recipes 機構とは別に、ツール横断の SKILL.md も利用可）
  • 弱点: 汎用フレーミングゆえコーディング機能がコード特化ツールに遅れることがある。学習曲線がやや急。あるベンチマークでは実行・完成度に課題（バックエンド3.1%、フロントエンド10.0%）
  • GitHub スター: 約43〜45K
  • バージョン目安: v1.25.0（2026年2月時点）

Cline CLI

  • 種別: Cline（VS Code 拡張）の CLI 版
  • Windows: ✅ WSL 不要（Node ベース）
  • 自律実行: モデル非依存の自律エージェント。計画・ファイル編集・コマンド実行・ブラウザ操作
  • スキル対応: ✅ Agent Skills（SKILL.md）対応
  • GitHub スター: 約61.6K（CLI 含むプロジェクト全体）

Crush（Charmbracelet）

  • 種別: Go 製の agentic コーディング TUI
  • Windows: ✅ WSL 不要（Go バイナリ）
  • 特徴: マルチプロバイダー、LSP 対応、リッチなターミナル UI
  • GitHub スター: 約24.1K

Continue CLI

  • 種別: OSS のターミナル拡張
  • Windows: ✅ WSL 不要（Node ベース）
  • 特徴: マルチモデル対応、ローカル/プライバシー重視。VS Code/JetBrains 版の CLI 版にあたる
  • GitHub スター: 約33.1K

Pi（pi-mono toolkit）

  • 種別: ミニマルで適応性の高いターミナルコーディング・ハーネス
  • Windows: 要確認（クロスプラットフォーム想定だが未検証）
  • 特徴: 統一 LLM API、TUI、MCP 対応
  • スキル対応: ✅ Skills 対応
  • GitHub スター: 約47.9K

Nanocoder

  • 種別: 「ローカルファースト」を謳う OSS
  • Windows: 要確認（Node ベースと思われるが未検証）
  • 特徴: ローカルモデルや OpenRouter などコントロール可能な API で使用。MCP サーバーの Dynamic tool loading 機能

Warp 2.0

  • 種別: AI 統合ターミナル。CLI エージェント機能を内蔵
  • Windows: ✅ WSL 不要。Windows ネイティブ版あり（2025年に対応）

5. IDE 統合型エージェント

エディタ内で動く。視覚的な差分、インライン補完、承認ワークフローを GUI で扱える。VS Code 拡張・スタンドアロン IDE はいずれも Windows ネイティブで動くため、このカテゴリは原則 WSL 不要。なお4強のうち IDE 型である Antigravity・Kiro は第2章を参照。

Cline（VS Code 拡張）

  • Windows: ✅ WSL 不要（VS Code にインストール）

8. Windows 11 ネイティブ（WSL 不要）実行可否による分類

ここまで紹介してきたツールを、本稿の主軸である Windows 11（Intel / Arm）で WSL を入れずに運用できるか という観点で分類し直す。なお第2章の4強は、いずれも下表「8-1」のネイティブ動作グループに含まれる。

ネイティブ実行時の注意:
  • Claude Code・Codex・Goose の CLI は Git for Windows（Git Bash）を入れておくと Bash ツールが使えて快適。無くても PowerShell にフォールバックするが、一部のシェルコマンドが Unix 前提で書かれていて失敗することがある。
  • パス区切り（\ vs /）、改行コード（CRLF vs LF）、ファイルパーミッション周りで、ネイティブ Windows 特有の摩擦がゼロではない。WSL2 はこれらを回避できるため「ネイティブで動くが、込み入った作業では WSL2 の方が快適」という評価も根強い。

8-2. WSL が必要 / 事実上必要なもの

ツール状況
OpenHands（ローカル実行）公式サポートは WSL2 + Docker。「Windows without WSL」のドキュメントページは存在するが、「公式サポート外・コミュニティ維持・動かない可能性あり」と明記。しかも no-WSL 構成ではブラウザツール非対応、.NET Core Runtime 必須、PowerShell 7+ 必須、Python 3.12/3.13 限定（3.14 不可）と制約が多い。実用上は WSL 前提と考えるべき
SWE-agent / mini-swe-agentLinux / Docker 志向の研究用ツール。Windows ネイティブ運用は想定外
sage（OSS オーケストレーター）「純 bash」のオーケストレーター。bash 環境必須。Git Bash で部分的に動く可能性はあるが Linux 志向
Docker を前提とするツール全般後述（8-4）の通り、Docker Desktop for Windows は標準で WSL2 バックエンドを使う。よって「Docker が要る」エージェントは間接的に WSL2 を要求することが多い

8-3. ローカルインストール不要（クラウド／ブラウザ型）── WSL の論点が無関係

ローカルに何もインストールしないため、Windows でも Mac でも「ブラウザがあれば使える」。WSL 有無は関係しない。

  • Devin（Cognition） ── クラウド自律エージェント
  • Jules（Google） ── クラウド自律エージェント
  • Genie / Manus ── クラウドプラットフォーム型
  • Codex のクラウド版 ── ChatGPT 統合のクラウド実行面（CLI 版は 8-1 に記載）
  • OpenHands のクラウドホスト版 ── ローカル版は 8-2 だが、クラウド版はブラウザから利用可
  • Factory（Droids）の Web / Slack / Linear 面 ── CLI 版もあるため一部ローカル（CLI は Node ベースで Windows ネイティブ動作の見込み）

8-4. 補足: Docker と WSL の関係

「Docker が必要」≒「WSL が必要」になりやすい点に注意したい：

  • Docker Desktop for Windows は、標準（既定）で WSL2 バックエンドを使う。Hyper-V バックエンドも選択可能だが、近年は WSL2 が既定かつ推奨。
  • ただし「Docker のために WSL2 機能を有効化する」のと「Ubuntu 等の Linux ディストロを入れて開発環境として常用する」のは別物。前者は Windows の機能としての WSL2 を有効にするだけで、Linux ディストロでの作業を伴わない軽量な使い方。
  • したがって OpenHands のような Docker 前提ツールを Windows で動かす場合、最低限「WSL2 機能の有効化」は避けられないことが多い。

8-5. 補足: Arm64 Windows での注意

Arm64（Snapdragon X 等の Copilot+ PC）では、ネイティブバイナリの提供有無がツールにより異なる：

  • Node.js / Python / Go / Rust はいずれも Arm64 Windows にネイティブ対応済み。よってそれらをベースにするツール（Gemini CLI・Qwen Code・Aider・OpenCode・Crush・Goose 等）は概ね Arm 機でも動く。
  • Claude Code は Arm64 Windows 対応。Electron 系 IDE（Cursor・Windsurf・VS Code・Antigravity・Kiro）も Arm64 Windows ビルドがある。
  • x64 専用バイナリしか配布されていないツールは、Windows on Arm のエミュレーションで動く場合もあるが、性能・互換性は要検証。
  • 実例として、Codex の GitHub Issue では Win11 25H2 ARM64 ユーザーが「VS Code 拡張のエージェントモードが WSL 必須」と指摘していた（その後ネイティブ Windows サンドボックスが実装され改善）。Arm 機ではこの種の「WSL を間接的に要求される」場面が Intel 機より出やすいので、導入前にネイティブ対応状況を確認するのが安全だ。

10. 注意点・補足

  • 「WSL 必須」と書かれた古い情報に注意 ── Claude Code・Codex・Goose については「Windows では WSL が必要」と書かれた記事が今も大量に残っているが、これらは2025年前半までの情報。現在はいずれもネイティブ Windows 対応済み。一次情報（各ツールの公式ドキュメント）で確認するのが安全。
  • ネイティブ動作でも Git for Windows は入れておく ── Claude Code・Codex・Goose の CLI は Git Bash があると Bash ツールが使えて摩擦が減る。無いと PowerShell フォールバックになり、一部の Unix 前提コマンドが失敗しうる。
  • 「ネイティブで動く」と「ネイティブが快適」は別 ── パス区切り・改行コード・ファイルパーミッションの差異で、込み入った作業では WSL2 の方が安定するという評価も根強い。WSL を完全に避けるか、Docker 用に WSL2 機能だけ有効化するかは運用方針次第。
  • ベンチマーク数値は変動が激しい ── SWE-bench Verified などのスコアはモデルのアップデートで頻繁に変わる。本稿の数値は2026年2〜5月時点の各種比較に基づく目安。
  • GitHub スター数はソースにより差が大きい ── プロジェクトの数え方（CLI 単体かリポジトリ全体か）で変わる。傾向把握用と考えるのが安全。
  • 自律ループの典型的な失敗 ── 「無限リファクタリングループ」（失敗テストを直そうとして新たなバグを生む）。Claude Code・OpenCode の build agent も陥りやすい。反復深度に上限を設け、Ctrl+C → git stash / git reset --hard で巻き戻し、より具体的なプロンプトで再開する運用が定石。
  • コンテキスト肥大 ── monorepo のルートで「ビルドを直して」と指示すると node_modules・ビルド成果物・vendor を読み込んでトークンを浪費する。
  • ローカル運用の選択肢 ── Ollama 経由で Codestral / DeepSeek Coder V2 / Qwen2.5-Coder 32B などを動かせば、Aider・Cline・Continue・OpenCode・Goose 等をモデルコストゼロで運用可能。これらはいずれも Windows ネイティブ動作するため、WSL 無しのローカル完結環境を組める。機密コードを一切外部送信したくない場合は Tabby（セルフホスト型）が選択肢。
